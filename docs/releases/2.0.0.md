## Compatibility

This is a **breaking revision**, including changes to authority and approval interpretation. The wire identifier remains `VERNACULUM-SCP-MS`; matching that identifier or a version string does not establish compatibility. Core changes still require explicit human-owner approval and canonical publication. Sessions never silently adopt revisions.

| Area | v2 contract and migration impact |
| --- | --- |
| Message grammar | YAML 1.2 core-schema mapping; prohibited YAML features remain excluded. IDs now use `agent-designation:locally-unique-token`. Sender, recipient and conversation may be supplied unambiguously by the authorised channel. |
| Core kinds | Seven kinds: `hello`, `ready`, `request`, `response`, `clarification`, `error`, `handoff`. `need`, `offer` and `amendment_notice` are no longer core kinds; reconsider each old exchange's meaning rather than mechanically renaming it. |
| Negotiation | Agree on the exact specification. A reply-bound `ready` uses the same establishment grammar version and selects an offered operating version. Cross-major negotiation needs shared grammar and explicit compatibility. |
| Extensions | Offer the complete set with exact definition identities; accept the whole set. Replacement, unilateral withdrawal and crossed proposals have explicit rules. Mutable branches/tags are not immutable definition references. |
| Responses | Statuses remain `completed`, `partial`, `failed`, `blocked`. Structured checks and clarification answers are defined. The v1.2.0 `feedback` preference contract is not defined in v2; its old meaning must not be assumed. |
| Errors | Codes are `malformed`, `unsupported_version`, `unsupported_extension`, `unknown_session`. Understood but unexecutable work gets a blocked response. |
| Handoffs | Core body uses `next`, replacing `next_action`. Acceptance requires a correlated completed response with `accepted_handoff: true`; it does not complete the underlying objective. |
| Trust and approval | Second-hand claims identify the approver and accessible evidence. Establish approval, scope and authority before consequential reliance; unverified claims remain non-governing. |
| Mutation and retries | State assumed base, exact operations and preconditions. Block affected mutation on an unknown or mismatched base. Recover unknown outcomes or obtain explicit duplication-aware authority before repeating potentially completed consequential work. |
| Durable records | Optional under explicitly agreed `x.vernaculum.records@1`; ordinary messages need no records. Records declare their agreed extension identity and immutable definition. |
| Record vocabulary | Six kinds replace eight: `evidence` covers observations/checks; `protocol_change` is no longer a Records kind. Relationships are reduced to six and use `{kind, target}`. |

## Migration guidance

1. Preserve existing sessions and historical records under their original contracts. Do not rewrite prior approval claims, timestamps, statuses or meanings to appear v2-compatible.
2. Establish canonical publication and the exact applicable v2 specification before adoption. Establish shared negotiation grammar and explicit compatibility for any cross-major exchange; otherwise use another authorised channel or fail.
3. Establish peer designations and unique message IDs. Replace old message templates only after agreement on the new operating contract. Do not treat old handoff acknowledgement as the new explicit responsibility acceptance.
4. If records are needed, explicitly negotiate the Records extension using the same exact definition on both sides. Ordinary core work can proceed without it.
5. Plan and authorise semantic record migration separately. The table below identifies structural changes, not a lossless converter or permission to infer missing information.

| Earlier record content | v2 requirement |
| --- | --- |
| `protocol_version` | Agreed `extension: {id, revision, definition}`; preserve original interpretation for historical revisions |
| `authority.basis` | Top-level `basis`; provenance does not establish truth or approval |
| `source_refs` | Optional `sources: [{ref, role}]`; `external` is not a v2 source role, so review meaning explicitly |
| `created_on` date | Original `created_at` in ISO 8601 UTC or `unknown`; never invent a time from a date |
| Revision number | Strictly increasing integer `record_version` starting at 1; preserve distinguishable historical revisions |
| Accepted requirement | Requires `approved_by`, `approval_ref` and established applicable authority |
| Proposal | Requires `target` and `open` alongside `change`, `rationale`, `acceptance_criteria` |
| `implementation_evidence`, `verification_result` | Review for `evidence` with `type: observation` or `check`, `target`, `observed`, `method`; checks also require `outcome` |
| Issue `next_action` | `next`; preserve the other required issue fields |
| Handoff | Uses `from`, `to`, `objective`, `confirmed`, `next`, `open`; acknowledged/completed states need actual acceptance/completion references |
| `protocol_change` and removed relations | Preserve under the original contract or define a separately agreed namespaced extension; do not invent v2 core equivalents |
| Revisions and replacement | Increment the version for the same ID; use acyclic `supersedes` only for authorised replacement of a different logical record |

The v2 record contract also requires a stable namespace-unique ID, kind, truthful status, subject, summary, actor (or `unknown`) and kind-specific content. Record meaning cannot rely solely on storage metadata. Missing evidence or references must be reported rather than reconstructed.

## Rollback

Restore the preceding protocol and current documentation through an authorised new change, then explicitly re-establish affected peer agreements. Preserve release history and distinguishable record revisions. Any future semantic migrations need their own rollback plan; this release performs no record migration or peer negotiation.
